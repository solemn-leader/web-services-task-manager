# Памятка для защиты

## Короткое объяснение проекта

Я выбрал менеджер задач с расчётом приоритета. Приложение состоит из четырёх контейнеров: Nginx с интерфейсом, сервер Node.js, PostgreSQL и отдельный сервис приоритезации. Пользователь добавляет задачи, задаёт срок и важность. Сервер сохраняет записи в базе. По кнопке расчёта он передаёт задачи отдельному сервису, получает баллы и возвращает результат интерфейсу.

## Демонстрация на три минуты

1. Запустить `docker compose up --build -d` и показать `docker compose ps`: четыре сервиса.
2. Открыть localhost:8088, нажать «Загрузить из БД» и показать начальные записи.
3. Добавить задачу со сроком сегодня и важностью 5.
4. Нажать «Рассчитать приоритет»: новая задача получает 85 баллов — 40 за важность и 45 за срок.
5. Перевести её в статус «Завершена»; при повторном расчёте она получает 0 баллов и уходит в конец списка.
6. Выполнить `docker compose down`, затем `docker compose up -d`, снова загрузить задачи. Запись остаётся благодаря именованному тому.

Это план демонстрации. До защиты нужно выполнить контейнерный запуск на своём компьютере; он не проводился при подготовке проекта по просьбе пользователя.

## Вопросы преподавателя

**Зачем отдельный сервис?** Он отвечает за один расчёт и общается с backend через HTTP. Его алгоритм можно менять независимо от базы и интерфейса.

**Как контейнеры находят друг друга?** В общей bridge-сети Docker разрешает имена сервисов. Backend использует адреса db:5432 и web-service:4000.

**Почему нет CORS?** Браузер обращается к тому же адресу frontend, а Nginx пересылает запросы `/api/` серверу. Для браузера источник один.

**Зачем healthcheck?** Запуск процесса ещё не означает готовность сервиса. Backend ждёт готовую БД и сервис приоритетов, frontend — готовый backend.

**Что хранит база?** Название, описание, важность, срок, статус, идентификатор и время создания задачи.

**Как избежать SQL-инъекции?** Значения передаются параметрами `$1`, `$2` и так далее, отдельно от SQL. HTML пользователя не вставляется в страницу: интерфейс использует textContent.

**Что происходит при ошибке веб-сервиса?** Backend возвращает 502 и понятное сообщение. Сохранённые задачи остаются в базе и доступны через обычную загрузку.

**Чем это отличается от полноценной системы микросервисов?** Здесь учебное разделение ответственности. Нет авторизации, распределённой трассировки, очередей или промышленной отказоустойчивости; они не требуются практикумом.
